## 2 队列与单次领取

状态仅为 DRAFT、READY、RUNNING、PASS、FAIL、BLOCKED、SUPERSEDED。NO_READY_TASK 是空队列说明，不是可执行状态。

1. 只读 fetch 队列分支，记录文档 HEAD。不要在用户旧工程执行 reset、clean 或 stash；使用隔离的文档工作区与源码构建工作区。先核对自身是否已经有运行中任务
2. 只有 READY 且必填字段完整、task_id + revision 未执行，才能领取。任务必须写明完整 40 位 code_sha，实际源码 checkout 必须匹配；不能以文档 HEAD、main 最新或任意本地 dirty 状态替代
3. 基于刚读到的远端 HEAD，把该任务改为 RUNNING，写入匿名执行者标识、唯一 run_id、JST 领取时间、结果路径；正常非强制推送。必须先确认远端领取提交成功，随后才启动命令
4. 并发 push 被拒时重新读取远端；不能把旧 READY 改动盲目 rebase 后再推。若已被领取、改 revision 或取消，则不执行。双方同时修改时仅针对仍匹配的 task_id/revision/run_id 做条件更新，保留他人新增资料。能使用 expected-head 比较时使用；禁止强推
5. 文档分支头前进不改变正在运行的固定源码身份。每轮记录队列 revision、领取提交和 code_sha；远端后续文档更新不应导致自动重跑
6. RUNNING 超时、断连、重启或领取后尚未启动，都不可直接抢占或重复领取。先检查原运行与已保存证据，不能因没有在线心跳就判定进程不存在。需要恢复时向助手/用户报告；只有明确的新 revision READY 才另起运行，旧记录保留
7. 结束后先提交结果文件，再仅在队列仍匹配自己的 task_id/revision/run_id 时改 PASS/FAIL/BLOCKED 并链接结果。若已被 SUPERSEDED 或替换，仍追加历史结果，但不覆盖新队列。验证远端结果存在

助手不在前一 RUNNING 未收尾时另发并发任务；SUPERSEDED 不授权强杀运行进程。失败重试必须新 revision，已 PASS 的结果不得覆盖为新一轮。

## 3 READY 任务必须给出的内容

- 唯一 task_id、revision、完整源码 SHA、任务文档固定链接/版本
- 受测变化、前置条件、干净源码与 bundle/EXE 身份检查
- 要执行的测试与顺序、期望、每阶段超时、失败后停止哪些依赖阶段
- 所需环境和隔离存档/诊断目录；缺能力则 BLOCKED，不改权限或绕过工具限制
- 对本轮创建进程/端口/profile 的所有权核验与有限收尾方法；不按进程名全局终止 Edge/Node/游戏，不清理不明资源

## 4 结果文件最小模板

每次使用新 run_id（例如 UTC 时间加随机后缀），最终记录追加保存，不能覆盖前轮。结果文件至少包含：

- task_id / revision / run_id / 队列领取提交 / 完整源码 SHA / tree / dirty 状态
- 开始、结束 JST 时间，OS 与实际 Node/Rust/浏览器等版本
- 命令及工作目录的脱敏相对位置；每条退出码、实际耗时、超时与人工干预情况
- 每阶段 PASS / FAIL / BLOCKED / NOT_RUN、实际统计、前置失败导致未执行的明确列表
- 首个错误、可复现步骤、期望与实际；主体错误和清理错误均保留
- 是否自然退出；本轮资源是否收尾，有未知残留就明确写未知
- 若构建：源码、最终 bundle、EXE 大小/SHA256及构建身份；若原生：对应版本/PID/窗口、隔离存档、真实操作及截图证据
- 证据文件相对路径与 hash，公开可安全提供的摘要；后续建议属于反馈，不自行排新任务

空 stdout、工具丢失退出码、超时后杀进程、测试 SKIP、mock 通过均不能写成完整通过。未见对应原生操作证据保持 Windows 待验证。新修改后旧通过只作历史。
